# チャット検索: 会話から候補ピンと口コミ評価へ

地図を検索したい範囲に合わせて「電源があるカフェ」と送ると、チャットが検索語と評価条件を決める。エリア・駅名は必須ではない。検索先は**送信時の地図の表示範囲**で、地名を指定しても地図をその場所に移して検索する機能はない。何を探したいか推定できない場合は聞き返す。

## 検索と評価の流れ

1. 周辺検索ではブラウザが前の実行を中断し、新しい `X-Run-Id` で `POST /api/chat` に会話履歴と表示範囲を送る。会話履歴はタブのメモリのみ。
2. `ToolLoopAgent` が `search_places` に `textQuery`、`evaluation`、`examples`（`1 ... x, 5 ... y`）、必要なら営業中条件や件数を渡す。手動検索と同じ[Places アダプター](places-new-adapter.md)が **Text Search Enterprise + Atmosphere 1 回**で最大 20 店の候補・表示情報・口コミを取得する。別途 Place Details は呼ばない。
3. **画面と会話モデルでは使うデータが異なる。** ブラウザは候補と付随する口コミを受け取り、ピンと一覧を表示する。会話モデルが検索結果への返答や次のターンに使うツール情報に口コミ原文は含めない。
4. 手動検索と同じ自動評価処理が、口コミ本文を店舗別の配列として `/api/analyze-reviews` に送る。最大 20 店、並列数を制限し、前の実行の結果は採用しない。色は条件スコアで、Google 評価とは別。採点時は根拠の口コミを番号で 1〜3 件選び、各原文とその投稿者を表示する。口コミがない店、または口コミから条件への適合度を判断できない店は採点済みに含めない。

## 今の候補を別の条件で並べ直す

入力欄の対象を「今の候補」にして新しい評価条件を送ると、検索時に取得した口コミで同じ店を再採点する。Places の呼び出しは増えないが、店舗別の OpenAI 採点には予算を使う。新しい周辺検索と再評価のどちらか判断できないときは、対象を確認してから実行する。

## 選択した店について質問する

店を選ぶと同じ入力欄の対象がその支店になる。「電源はどの席にある？」と質問すると、選択中の支店の取得済み口コミだけを使う。質問しても候補・採点は維持され、Google Places は呼ばない。

`POST /api/place-question` は回答と根拠の口コミ番号（1 始まり、重複なし、最大 3 件）を返す。根拠を開くと原文・投稿者・リンクを確認できる。根拠がないときは「口コミからは分からない」と答える。質問履歴は現在の検索内で店舗別に持ち、別の支店の会話を混ぜない。直近のやり取りは質問の文脈にのみ使い、回答の根拠にはしない。

質問は 300 字まで、送信する履歴は同じ店舗の直近 3 往復。各質問は独立した実行 ID を持つ。口コミ 0 件なら外部呼び出しなし、それ以外は `openai.chat` 1 回を予約する。ローカルで架空の口コミ 2 件を使った実モデル確認では、窓側の電源について述べた 1 番だけが回答の根拠に選ばれた。

## 候補 2 店への徒歩時間を比べる

出発したい場所に地図の中心を合わせて比較を開始し、候補 2 店を指定する。出発地は開始時点で固定され、その後で地図を動かしても変わらない。比較は店から店の移動ではなく、同じ出発地から各店への徒歩時間を Google Routes の Compute Route Matrix（`WALK`）で求める。1 出発地 × 2 目的地なので台帳は `routes.matrixElement` を 2 要素予約する。

`POST /api/walking-comparison` に固定した `origin: { lat, lng }` と異なる 2 件の `placeIds` を送る。サーバー専用の `GOOGLE_ROUTES_SERVER_API_KEY` がなければ 503 `ROUTES_UNAVAILABLE`。経路なしは該当店の `durationSeconds: null`、上流エラーはエラーとして返し、Places キーや直線距離からの時間推定で代用しない。

## モデル・予算・エラー

会話は Vercel AI SDK の `ToolLoopAgent` と `gpt-5.6-luna`（Responses API、`reasoningEffort: "none"`、`store: false`）。`useChat` が UI メッセージストリームを受ける。[エージェント](../src/lib/chat-agent.ts)／[ツール契約](../src/lib/chat-contract.ts)／[ブラウザ側](../src/lib/chat-transport.ts)

`X-Session-Id` / `X-Run-Id` は UUID v4。最初のモデルステップはストリーム開始前に予約し、その後もステップ単位で予約・精算する。Places は `places.search` 1 回、後続の採点は店舗別の `openai.analyze`。すべて同じ実行 ID に計上し、店舗数分の Google 詳細予約は作らない。[予算台帳](budget-ledger.md)

開始前の入力エラー・予算超過・台帳障害は HTTP 400 / 429 / 503 と `{ error: { code, message } }`。開始後のモデルエラーはストリームのエラーチャンクに同形式を載せる。検索ツールの既知の失敗はツール結果で伝え、成功候補として描画しない。

以前の一括検索の[実 API 記録](verification-bundled-search.md)は、その時点の検索・採点に関するもの。徒歩比較や現在の画面の検証結果ではない。
