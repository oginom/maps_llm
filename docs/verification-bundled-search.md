# 一括チャット検索の実 API 確認（2026-11-20）

以下の実測値は、モデルが抜粋を生成し、文字列照合で投稿者を特定していた旧方式の記録。現行の口コミ番号方式では実 API 計測をしていない。

## 旧方式で完走した計測

ローカル開発サーバーで、渋谷駅周辺の固定範囲（南 35.651、北 35.669、西 139.692、東 139.711）と「電源があるカフェ」を新規セッション・実行 ID で送信。地名の聞き返しなしで候補が届き、チャットストリームは正常終了した。実行は 1 回、再試行なし。

| ローカルクライアントでの観測点 | チャット送信開始から |
| --- | ---: |
| `search_places` の候補 20 件を受信・検証 | 3.965 秒 |
| 5 件目の採点成功 | 6.877 秒 |
| 最後の採点成功（20 / 20 件）・全処理終了 | 13.449 秒 |

### 現行方式の確認方法

1. Node 24.20.0 で `node --test scripts/verify-bundled-search.test.mjs` を実行（外部通信なし）。合成データでストリーム処理、採点、根拠不足、複数の根拠番号と各原文への帰属を確認する。
2. ローカル開発サーバーとファイル台帳を使用し、`node scripts/verify-bundled-search.mjs` を **1 回だけ**実行する（実 API を使う）。必要なら `PORT` と `LEDGER_FILE` を開発サーバーに合わせる。クライアントは候補・口コミ・抜粋をファイルに保存せず、集計だけを出力する。
3. `scores` は数値で採点した店舗数、`unknown` は根拠不足の店舗数、`scoreErrors` は処理が失敗した店舗数。採点時間は数値スコアだけを対象にする。`citedReviews` は根拠に選ばれた口コミの総件数、`citedReviewsWithAuthor` はそのうち投稿者名がある件数。1 店に複数の根拠があり得るため、旧方式の店舗単位の照合率とは比較できない。
4. 旧計測のトークン内訳は、他の操作をしない計測区間で増えた開発ログの `api/chat` と `api/analyze-reviews` の利用量から集計した。

## 先行計測（途中停止）

渋谷周辺を表示範囲にして、ローカルの `/api/chat` に「電源があるカフェ」を 1 回送信した。HTTP 200。地名の聞き返しを挟まず `search_places` が呼ばれ、候補と口コミを含む応答が届いた。

検証クライアントが候補イベントの JSON を読み切れず、`SyntaxError` で停止した。採点リクエストは 0 件。候補総数、候補到着時間、5 件目・最終採点までの時間、抜粋と投稿者の照合率は未測定。サーバーログの 2.455 秒はチャットルートの記録で、候補到着時間ではない。ブラウザー上の成否は判断できない。
